# 一些问与答
- 学生问：vm.c运行在什么mode下？\
老师回答：vm.c中的所有函数都是内核的一部分，所以运行在supervisor mode
- 学生问：难道vm.c里的函数不是要直接访问物理内存吗？\
老实回答：是的，这些函数能这么做的原因是，内核小心的在page table中设置好了各个PTE。
这样当内核收到了一个读写虚拟内存地址的请求，会通过kernel page table将这个虚拟地址内
存地址翻译 成与之等价物理内存地址，再完成读写。所以，一旦使用了kernel page table，
就可以非常方便的在内核中使用所有这些直接的映射关系。但是直到trap机制切换到内核之前，
这些映射关系都不可用。直到trap机制将程序运行切换到内核空间之前，使用的仍然是没有这些
方便映射关系的user page table。\
- 学生问：read和write系统调用，相比内存的读写，它们的代价都高的多，因为它们需要切换模式，并来回倒腾。
- 有没有可能当你执行打开一个文件的系统调用时，直接得到一个page table映射，而不是返回一个文件描述符？
- 这样只需要向对应于设备的特定地址写数据，程序就能通过page table访问特定的设备。你可以设置好限制，就像
- 文件描述符只允许修改特定文件一样，不需要像系统调用一样在用户空间和内核空间来回倒腾了。\
老师回答：这是一个很好的想法。实际上很多操作系统都提供这种叫作内存映射文件（memory-mapped file access）的
机制，在这个机制里面通过page table，可以将用户空间的虚拟地址空间，对应到文件内容，这样就可以通过内存地址直接
读写文件。实际上，将会在mmap实验中完成这个机制。对于许多程序来说，这个机制的确会比直接调用read/write系统调用
要快很多。
