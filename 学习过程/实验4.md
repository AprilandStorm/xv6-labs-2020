# 一些问与答
- 学生问：vm.c运行在什么mode下？\
老师回答：vm.c中的所有函数都是内核的一部分，所以运行在supervisor mode
- 学生问：难道vm.c里的函数不是要直接访问物理内存吗？\
老实回答：是的，这些函数能这么做的原因是，内核小心的在page table中设置好了各个PTE。
这样当内核收到了一个读写虚拟内存地址的请求，会通过kernel page table将这个虚拟地址内
存地址翻译 成与之等价物理内存地址，再完成读写。所以，一旦使用了kernel page table，
就可以非常方便的在内核中使用所有这些直接的映射关系。但是直到trap机制切换到内核之前，
这些映射关系都不可用。直到trap机制将程序运行切换到内核空间之前，使用的仍然是没有这些
方便映射关系的user page table。\
- 学生问：read和write系统调用，相比内存的读写，它们的代价都高的多，因为它们需要切换模式，并来回倒腾。有没有可能当你执行打开一个文件的系统调用时，直接得到一个page table映射，而不是返回一个文件描述符？这样只需要向对应于设备的特定地址写数据，程序就能通过page table访问特定的设备。你可以设置好限制，就像文件描述符只允许修改特定文件一样，不需要像系统调用一样在用户空间和内核空间来回倒腾了。\
老师回答：这是一个很好的想法。实际上很多操作系统都提供这种叫作内存映射文件（memory-mapped file access）的机制，在这个机制里面通过page table，可以将用户空间的虚拟地址空间，对应到文件内容，这样就可以通过内存地址直接读写文件。实际上，将会在mmap实验中完成这个机制。对于许多程序来说，这个机制的确会比直接调用read/write系统调用要快很多。 
- a标志位表示这条PTE是不是被代码访问过，是不是曾经有一个被访问过的地址包含在这个PTE的范围内。d标志位表明是否曾经有写指令使用过这条PTE。这些标志位由硬件维护以方便操作系统使用。对于比XV6更复杂的操作系统，当物理内存吃紧的时候，可能会通过将一些内存写入到粗盘来，同时将相应的PTE设置为无效，来释放物理内存page。可以查看a标志位来判断这条PTE是否被使用过，如果他没有被使用或者最近没有被使用，那么这条PTE对应的page适合用来保存在磁盘里。不过XV6没有这样的策略。
