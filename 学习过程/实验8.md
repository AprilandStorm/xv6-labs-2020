#Q&A
| 对象     | 属于谁的资源                  | 是否并发执行 | 是否调度开销大        | 是否可在用户空间切换 | 操作系统是否感知 |
| ------ | ----------------------- | ------ | -------------- | ---------- | -------- |
| **进程** | 独立内存空间、文件描述符、地址空间等      | ✅      | 非常大（上下文切换开销最大） | ❌（只能由内核调度） | ✅        |
| **线程** | 属于进程的轻量级执行单元，**共享进程资源** | ✅      | 较大（切换需内核参与）    | ❌（由内核调度）   | ✅        |
| **协程** | 用户空间中的控制流，通常运行在**线程内**  | ❌（伪并发） | 非常小（切换只改寄存器栈）  | ✅（完全用户空间）  | ❌        |
1. 进程（Process）
是操作系统分配资源的最基本单位；每个进程有自己独立的地址空间、栈、堆、文件描述符；不同进程之间内存隔离，需要使用 IPC（如管道、共享内存）通信；创建和切换进程的开销最大（如 fork()、exec()）；由操作系统内核调度
2. 线程（Thread）
是进程内部的执行单元，也称“轻量级进程”；多个线程共享进程资源（内存地址空间、文件描述符等）；每个线程拥有自己的寄存器上下文和栈；切换线程需要进入内核态，但比切进程轻；由操作系统调度（内核线程）；
3. 协程（Coroutine）
是运行在用户空间的轻量级线程；一般工作在一个线程内（多协程共享一个线程）；协程切换不需要内核参与，只需保存/恢复寄存器、栈指针等，非常快；典型应用：异步编程（如 Python 的 async/await、C++20 的 co_await、Go 协程）；操作系统完全不知道协程的存在，调度由用户空间库完成（如 libco, ucontext, boost::coroutine）；不是真并发，多个协程不能真正同时运行（除非用多线程 + 多协程）。
| 特性      | 协程      | 线程     | 进程     |
| ------- | ------- | ------ | ------ |
| 运行空间    | 用户空间    | 用户+内核  | 用户+内核  |
| 切换成本    | 非常低     | 中等     | 非常高    |
| 并发支持    | ❌（伪并发）  | ✅（真并发） | ✅      |
| 是否被内核感知 | ❌       | ✅      | ✅      |
| 共享资源    | 栈/上下文独立 | 地址空间共享 | 完全独立   |
| 使用场景    | 高并发、异步  | 并行计算   | 安全隔离任务 |

# lab 8 locks
重新设计代码以降低锁竞争，提高多核机器上系统的并行性。

## memory allocator
通过拆分 kmem 中的空闲内存链表，降低 kalloc 实现中的 kmem 锁竞争
- 原理与分析:
1. kalloc 原本的实现中，使用 freelist 链表，将空闲物理页本身直接用作链表项（这样可以不使用额外空间）连接成一个链表，在分配的时候，将物理页从链表中移除，回收时将物理页放回链表中。
2. 分配物理页的实现（原版),无论是分配物理页或释放物理页，都需要修改 freelist 链表。由于修改是多步操作，为了保持多线程一致性，必须加锁。但这样的设计也使得多线程无法并发申请内存，限制了并发效率。kmem 是整个系统中竞争最激烈的锁
3. 这里体现了一个先 profile 再进行优化的思路。如果一个大锁并不会引起明显的性能问题，有时候大锁就足够了。只有在万分确定性能热点是在该锁的时候才进行优化，「过早优化是万恶之源」
4. 这里解决性能热点的思路是「将共享资源变为不共享资源」。锁竞争优化一般有几个思路：只在必须共享的时候共享（对应为将资源从 CPU 共享拆分为每个 CPU 独立）;必须共享时，尽量减少在关键区中停留的时间（对应“大锁化小锁”，降低锁的粒度）
5. 该 lab 的实验目标，即是为每个 CPU 分配独立的 freelist，这样多个 CPU 并发分配物理页就不再会互相排斥了，提高了并行性
6. 但由于在一个 CPU freelist 中空闲页不足的情况下，仍需要从其他 CPU 的 freelist 中“偷”内存页，所以一个 CPU 的 freelist 并不是只会被其对应 CPU 访问，还可能在“偷”内存页的时候被其他 CPU 访问，故仍然需要使用单独的锁来保护每个 CPU 的 freelist。但一个 CPU freelist 中空闲页不足的情况相对来说是比较稀有的，所以总体性能依然比单独 kmem 大锁要快。在最佳情况下，也就是没有发生跨 CPU “偷”页的情况下，这些小锁不会发生任何锁竞争。
7. 这里选择在内存页不足的时候，从其他的 CPU “偷” 64 个页，这里的数值是随意取的，在现实场景中，最好进行测量后选取合适的数值，尽量使得“偷”页频率低。UPDATE 2022-04-14: ”偷“的代码可能产生死锁（cpu_a 尝试偷 cpu_b，cpu_b 尝试偷 cpu_a），可能的解决方案看本文评论区或 [https://github.com/Miigon/blog/issues/8]
